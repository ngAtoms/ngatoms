# Data Grid Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `nga-grid`, a data grid for data-heavy applications: hierarchical rows, multi-level column headers, two-axis virtualization, number formatting, column header filters and sorting, and spreadsheet-style editing — with zero runtime dependencies.

**Architecture:** Two registry entries. `grid-core` is plain TypeScript (no Angular) and owns every model and algorithm. `grid` is the Angular renderer that draws what the core computes and turns DOM events into core commands. The app owns the data: the grid emits changes and never mutates rows, runs no formulas, and applies no business rules.

**Code standard:** KISS, SOLID and Clean Code; no `//` comments; a `@file` header per file and a JSDoc header per function. Enforced by ESLint for `grid-core/` and `grid/` (see `CLAUDE.md` → Code Standards).

**Tech Stack:** Angular 22 (zoneless, signals), TypeScript 6, `Intl.NumberFormat`, plain CSS custom properties, Vitest for `grid-core`.

**Decision record:** `docs/adr/0001-data-grid.md`

> **Scope of this document:** it fixes the chunks, their order, the files, and what "done" means for each. It does not contain the code. Each chunk gets its own detailed, code-level plan when work on it starts, so later chunks can absorb what earlier ones teach us.

**Performance budget (checked from Chunk 2 on):** 100k rows × 500 columns in memory; scroll at 60 fps on a mid-range laptop; initial render under 100 ms; expand/collapse of a 10k-row branch under 50 ms.

## Chunk 1: Core models

**Outcome:** everything needed to know *what* to draw, with no DOM.

### Task 1.1: Column model
- [x] Flatten the column tree to leaves; compute header rows with column spans.
- [x] Split leaves into pinned-left / center / pinned-right.
- [x] Widths with prefix sums; binary search from offset to column index.
- [x] Specs: spans for uneven group depths, pinning, resize updates sums.

### Task 1.2: Row model
- [x] Build the tree from flat rows + `parentId`; compute `level`.
- [x] Produce the visible list for a given expanded set. *(No incremental update: a full re-flatten of 100k rows takes ~6 ms, well inside the 50 ms budget, so the simpler code stays.)*
- [x] `hasChildren` without children; placeholder entries for rows not loaded yet; `rowCount` larger than the rows supplied (`windowedRows`, flat data only).
- [x] Specs: deep trees, orphan rows, collapse of a large branch, sparse windows.

### Task 1.3: Viewport
- [x] Visible row and column ranges from scroll offsets, viewport size, overscan.
- [x] Total scroll size; pinned regions excluded from the scrolling axis.
- [x] Specs: edges, zero-size viewport, overscan clamping.

### Task 1.4: Filter model
- [x] `filter.ts`: filter types (`text`, `number`, `set`), operators, and predicates over raw values.
- [x] Apply a `filters` map to the row model: matching rows plus their ancestors; ancestors that do not match are flagged so the renderer can dim them.
- [x] Distinct values of a column for the `set` filter. *(Computed on demand; caching per data version moves to the renderer, which knows when data changes.)*
- [x] External mode: the caller simply does not pass a filter result to `flattenRows`; the mode switch itself lives in the renderer (Chunk 3).
- [x] No totals are recalculated; parents keep the values they were given.
- [x] Specs: each operator, empty values, tree context, combined filters across columns, external mode.

### Task 1.5: Sort model
- [x] `sort.ts`: comparator from a `sort` list — numeric for numbers and decimal strings, collator for text, empty values last.
- [x] Row model orders siblings within each parent; the tree shape is untouched.
- [x] External mode: the caller does not pass a comparator; the mode switch lives in the renderer (Chunk 3).
- [x] Specs: numbers, decimal strings, text, empties, descending, nested levels, stability.

### Task 1.6: Benchmark
- [x] `npm run bench --workspace=packages/primitives` builds 100k × 500 and times flattening, expand/collapse, range lookup, applying a filter, and sorting.
- [x] Baseline recorded below. *(The gate is a fixed budget per operation, several times the baseline, rather than "20% slower than last run": a relative gate flakes on shared CI machines, while a budget still catches an algorithm going quadratic.)*

| Operation (100,000 rows × 505 columns) | Median | Budget |
|---|---|---|
| Build row tree | 8.2 ms | 150 ms |
| Flatten, everything expanded | 5.7 ms | 50 ms |
| Flatten after collapsing a 10k-row branch | 6.3 ms | 50 ms |
| Flatten, siblings sorted by amount | 48.8 ms | 400 ms |
| Apply a text filter | 11.7 ms | 150 ms |
| Flatten a filtered tree | 5.8 ms | 50 ms |
| Build column model | 0.24 ms | 10 ms |
| Visible ranges for one scroll frame | 0.002 ms | 0.5 ms |

Measured 2026-11-13 in a Linux VM on Node 22; treat as indicative, not as the reference machine.

**Done when:** specs pass and the benchmark meets the budget for model operations.

## Chunk 2: Read-only rendering

**Outcome:** a grid you can look at and scroll. → *Tree grid preset.*

### Task 2.1: Shell and panes
- [x] `nga-grid` lays out header / body / footer × left / center / right panes.
- [x] One scroll container drives all panes. Pinned panes and the header use `position: sticky` inside it, so there is no scroll syncing in JavaScript at all.
- [x] `ResizeObserver` feeds the viewport size to the core.

### Task 2.2: Virtualized body
- [x] Render only the core's visible ranges; position rows and cells by offset.
- [x] Rows are recycled by pool slot (`index % poolSize`), so scrolling rebinds existing elements instead of recreating them; cells track by column id.
- [x] Placeholder rendering for rows not loaded yet; `visibleRangeChange` emits whenever the rendered window changes. *(Not debounced: the app knows its own fetch cadence better than the grid does.)*

### Task 2.3: Headers
- [x] Multi-level column group headers with spans, aligned to virtualized columns.
- [x] Row header column(s): indentation per level, expand/collapse toggle, emits `rowExpand` for lazy children.

### Task 2.4: Formatting
- [x] `format.ts`: accounting negatives, scale, zero display, percent, decimals, sign reversal; formatter cache per format key.
- [x] Resolution order: column default → row override. *(A per-cell override waits for the cell-state resolver in Chunk 4.)*
- [x] Variance columns colored by the row's `favorable` direction, using status tokens. Negatives keep their minus or parentheses, so the reading never depends on color alone.
- [x] Specs for every format option across two locales.

### Task 2.5: Styles
- [x] `grid.styles.css` with `--nga-grid-*` variables over the tokens; compact and comfortable densities; total/subtotal row and column treatments; pinned-pane shadows.

### Task 2.6: Docs
- [x] Docs page with an income statement demo (tree rows, months grouped by quarter, variance columns), light and dark, plus a 100,000 × 500 demo.
- [x] Group header labels stick to the left edge of the scrolling area, so they stay readable while a group is partly in view.

**Done when:** the demo scrolls 100k × 500 within budget in Chrome, Firefox and Safari, and both themes look right.

**Status:** built and checked in headless Chrome only. With 100,000 rows × 505 columns the DOM holds about 190 cells. A worst-case scroll test (15 rows and 60 px sideways on every frame, software rendering, no GPU) measured ~6 ms of script, ~2 ms of style and ~3 ms of layout per frame. Still open:

- [ ] Check scrolling on real hardware in Chrome, Firefox and Safari.
- [ ] The docs preview card's `backdrop-filter` dominated paint time in that test (≈80 ms per frame with it, ≈17 ms without). Confirm it is a software-rendering artifact, or drop the filter around grid demos.

## Chunk 4: Editing

**Outcome:** data entry. → *Editable grid preset.*

### Task 4.1: Edit session
- [ ] `edit.ts`: start (type-to-edit, F2, double-click), commit (Enter moves down, Tab moves right), cancel (Escape).
- [ ] `parse.ts`: localized number parsing — separators, parentheses, percent, scale suffixes.
- [ ] Editor component positioned over the cell, sized to it, never clipped by a pane edge.

### Task 4.2: Change emission
- [ ] Every edit emits `cellsChange` with a `CellChange[]` batch. The grid does not write to rows.
- [ ] Editing a parent cell emits exactly one change; no spreading.
- [ ] Docs recipe: the app receives the batch, applies its own rules (including spreading and totals), and passes treated rows back.

### Task 4.3: Cell state
- [ ] `cellState(row, column)` resolver: `readonly`, `locked`, `calculated`, `dirty`, `invalid`, `pending`, `note`.
- [ ] Visual treatment and accessible description for each; non-editable states block the editor.
- [ ] `note` shows a marker and emits `noteRequest`; no built-in popover.

### Task 4.4: Paste and fill
- [ ] `clipboard.ts` parse: TSV from Excel/Sheets → one `cellsChange` batch; skips non-editable cells and reports them.
- [ ] Paste a single value into a range; paste a block larger than the selection.
- [ ] Fill down / right (Ctrl+D / Ctrl+R) and fill handle drag. Fill copies values only.

### Task 4.5: Undo / redo
- [ ] `history.ts`: stack of batches; Ctrl+Z / Ctrl+Y emit inverse batches as ordinary `cellsChange` events.

### Task 4.6: Docs
- [ ] Data entry demo: editable leaf cells, calculated totals owned by the demo app, locked actuals, paste from Excel, a parent edit spread by the demo app.

**Done when:** a sheet can be keyed in and pasted from a spreadsheet end to end, with every data change flowing through `cellsChange`.

## Risks to watch

| Risk | Mitigation |
|---|---|
| Scroll sync between panes jitters | One scroll container, panes positioned by transform; verify in Safari early (Chunk 2). |
| Focus is lost when the active cell is virtualized away | Dedicated task (3.3) with its own test page before editing builds on it. |
| Performance regresses unnoticed | Benchmark from Chunk 1, re-run at the end of every chunk. |
| Filtered totals are expected to "just work" | Document clearly that client filtering never recalculates parents; show the external-mode recipe that returns filtered totals. |
| Browsers cap element height (about 17.8M px in Firefox, 33.5M in Chrome), which is ~600k compact rows | Fine for the 100k target. Past that, page by scroll in windows or add scroll scaling; decide when a real case needs it. |
| Scope creep toward business logic | The ADR is the gate: anything that computes or decides belongs to the app in this version. |
| Editing doubles the surface | Chunks 2–3 ship a usable read-only grid first; editing builds on a stable base. |

## After v1 (not planned here)

Multi-column sorting; a calculation variant on the same core (formulas, spreading strategies, rollups, filtered totals); variable row heights; row and column reordering; RTL and touch; built-in note popover.
